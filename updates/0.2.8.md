# v0.2.8

## 変更内容

- 通常起動の更新確認をバックグラウンドで実行し、GitHubやDNSの応答待ちで出席操作の開始・終了を遅らせないようにしました。
- 成功した更新情報は原則24時間再利用します。通信失敗時や利用制限時は従来の再試行間隔を維持します。
- UIを開く直前の通知出力をやめ、起動後に確認が完了した場合も画面内の更新案内へ反映します。
- CLIの入力中には通知を割り込ませず、起動時の保存済み情報と処理終了時に取得済みの新情報を案内します。
- 自動実行（`--scheduled`）で登録時刻の範囲指定がある予定でも、分境界をまたいだ直後（2分以内）の実行を取りこぼさないようにし、実行中の排他予約と完了時のみの実行記録（`logs/schedule-runs.json`）によって確認実行（`--check` / `dry_run`）や送信前の失敗で当日の本番実行を消費せず、同日の重複実行を防ぎます。
- 自動実行の LaunchAgent 設定に `logs/launchagent.log` へのログ出力先を追加し、アプリ起動前のエラーも安全な診断情報として記録するようにしました。
- 自動実行の登録（`launchctl bootstrap`）が失敗した際、以前の設定ファイルと登録状態の復元を試み、失敗内容を記録するようにしました。

## 利用者の操作

- `att update` で更新し、画面を開き直してください。
- 更新案内が出た場合は `att update --notes` で内容を確認し、`att update` で更新してください。手動コマンドはキャッシュの期限内でも最新情報を取得します。
- 更新確認を無効にする場合は、引き続き `ATTENDANCE_NO_UPDATE=1 att --ui` を使えます。通常起動ではアプリ本体や依存パッケージの自動更新は行いません。
- 自動実行を利用中の場合は、更新後に `att schedule install`（または GUI の予定画面で `I` を押して停止→開始）を実行すると最新のログ出力設定が反映されます。
- 自動実行で失敗した場合は `logs/attendance-*.log` とあわせて `logs/launchagent.log` を確認してください（共有時は個人・機微情報を含めないようご注意ください）。
