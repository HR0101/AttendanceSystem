# Issue #23: 更新確認で起動を待たせない

対象: https://github.com/HR0101/AttendanceSystem/issues/23

## 再現と修正

`tests/test_update_notifications.py` の `test_slow_network_does_not_block_application_start_or_exit` は、更新通信をイベントで停止させ、その間にアプリが起動・終了できるかを検証する。修正前は「更新通信の完了待ちでアプリが起動しない」で失敗した。実ネットワーク、大学、Keychainは使用しない。

通常起動はデーモンスレッドで更新情報だけを確認する。ワーカーは共有の実行ロックと非ブロッキングのダウンロードロックを使い、端末には出力しない。成功した結果は既存の24時間キャッシュを利用する。UIはローカルキャッシュを1秒間隔で再読込し、起動後に届いた情報も表示する。CLIは起動時と処理終了時に取得済みの情報を案内するが、通信の終了待ちはしない。

## 回帰確認

- 遅い通信中もアプリが起動・終了でき、アプリの終了コードを維持する。
- 通常起動はJSONのみを取得し、ZIP・依存準備・更新適用をしない。
- 24時間以内のキャッシュは再利用し、期限切れは再取得する。
- オフライン時はログへ記録し、1時間の再試行抑止を維持する。
- UI起動前のstderr出力をなくし、起動後のキャッシュ更新を画面へ反映する。
- CLIの同じ通知は重複せず、ワーカーから入力中の端末へ出力しない。
- ロック競合とスレッド作成失敗でも、出席アプリの起動を妨げない。
